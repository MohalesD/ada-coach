## 3. Policy audit — every table, every command

Full `pg_policies` dump captured for `public` and `storage` (raw data available on request; the
findings table below is the actionable summary).

**Anon access:** zero policies grant anything to `anon` on `public` or `storage`. Every policy
role is either `{service_role}` or `{authenticated}`. This matches the original 2026-04-18
audit's claim ("Anonymous role is locked out everywhere") and it still holds.

**USING/WITH CHECK scoping:** every own-rows table (`conversations`, `sessions`, `assumptions`,
`products`, `folders`, `market_briefs`, `market_evidence`, `competitors`, `competitor_evidence`,
`assumption_evidence`, `blind_spots`, `interview_guides`, `reports`, `model_usage`,
`user_feedback`, `portfolio_profiles`, `portfolio_projects`) scopes both clauses to
`user_id = auth.uid()`. `user_profiles` scopes to `id = auth.uid()`. `messages` scopes via a
join to `conversations.user_id = auth.uid()`, and its `feedback`-column UPDATE policy
additionally requires `role = 'assistant'`. `app_settings` scopes via a `user_profiles.role =
'owner'` subquery on every command. This is sound and consistent.

**One real gap — `documents` "owner insert" policy:**
```
with_check: EXISTS (SELECT 1 FROM user_profiles
                     WHERE user_profiles.id = auth.uid()
                       AND user_profiles.role = 'owner')
```
This checks that the **caller** is owner but does **not** constrain the inserted row's
`user_id` to `auth.uid()`. An owner-authenticated INSERT into `documents` could set `user_id` to
any UUID, attributing a global-corpus document to a different user. Blast radius is
self-inflicted-only (only the trusted owner role can reach this path), and `document_chunks`'
own INSERT policy independently re-checks `d.user_id = auth.uid()`, so a chunk write for a
misattributed document would still be blocked via that second policy. Low severity, but it is a
real gap in the intended invariant and should be tightened — `and user_id = auth.uid()` in the
WITH CHECK, mirroring every other own-rows table.

**Storage bucket policies — resolves a live doc contradiction.** `storage.objects` carries
exactly three policies (`upload`/`read`/`delete` to `own documents folder`), all scoped to
`bucket_id = 'documents' AND (storage.foldername(name))[1] = auth.uid()::text` — **no role
check**. This is the Run 3 hardening migration
(`20260705100000_storage_session_uploads.sql`) working exactly as designed: any authenticated
user can upload to their own folder.

`tasks/todo.md`'s backlog table currently claims: *"Storage policies for non-owner session
uploads — 🔲 Open. Session file uploads to the `documents` bucket still require the owner role.
**Blocks Spec 1 testing if a non-owner ever uploads**."* **This is stale and wrong** — verified
against the live policy definitions, which match the Run 3 migration exactly. This is a
read-only diagnostic and `tasks/todo.md` is explicitly out of scope for edits per this
session's plan of record, so the correction is recorded here rather than applied to the file.

## 4. `SECURITY DEFINER` functions reachable by non-admin roles

Three functions carry public/authenticated `EXECUTE` per the advisor. Each was read in full:

- **`fn_reset_credits_if_due()`** — checks `auth.uid() IS NULL` first and returns `NULL`
  immediately for `anon` (no JWT → `auth.uid()` is null under PostgREST). For `authenticated`,
  it only ever reads/writes the caller's own row (`where id = v_user_id`). Direct RPC exposure
  is real but functionally inert beyond what the caller could already do to their own row.
- **`handle_new_user()`** — references `new.id` / `new.email`, which only exist in a trigger
  execution context (`AFTER INSERT ON auth.users`). A direct RPC call outside a trigger context
  has no `NEW` record and errors immediately. Exposure is real but not exploitable via direct
  invocation.
- **`log_assumption_status()`** — same shape as above: references `new`/`old`, trigger-only,
  errors if invoked directly as RPC.

**Verdict:** none of the three are actively exploitable via direct RPC call today, but all three
should have `REVOKE EXECUTE FROM anon, authenticated` as hygiene — the advisor is correct that
this is unnecessary surface area, even though the practical risk is near-zero given each
function's internal guards.

**Not flagged by the advisor, worth noting as a genuinely good pattern:** `rls_auto_enable()` is
an `event trigger` function (`RETURNS event_trigger`) that automatically runs `ALTER TABLE ...
ENABLE ROW LEVEL SECURITY` on every new `CREATE TABLE` in `public`. Event trigger functions
cannot be invoked via RPC at all — Postgres rejects any attempt outside the automatic
event-trigger context. This means it is structurally impossible to add a new public table to
this project and forget RLS. Positive finding; do not remove or weaken it.

## 5. Column-level grants — the finding that most changes the picture

`information_schema.column_privileges` for `user_profiles` and `messages` (the two tables the
2026-04-18 audit's "column-level GRANTs" section describes as locked down):

**`user_profiles`, `authenticated`:** only `UPDATE(display_name)` is granted for UPDATE. No
`UPDATE(role)`, no `UPDATE(id)`, no `UPDATE(email)`, no `UPDATE(credits_remaining)`. **The
critical fix from 2026-04-25 (self-elevation to `owner`) is confirmed still in effect.**

**But:** `authenticated` *also* holds `INSERT`, `SELECT`, and `REFERENCES` on nearly every
column of `user_profiles`, including `role`, `credits_remaining`, `email`, and `id`. **And
`anon` holds the same broad `INSERT`/`SELECT`/`UPDATE`/`REFERENCES` grant across essentially
every column of `user_profiles`, including `role`** — this is not restricted to `authenticated`
at all.

Same pattern on `messages`: both `anon` and `authenticated` carry `INSERT`/`SELECT`/`UPDATE`/
`REFERENCES` across nearly all columns (`content`, `role`, `conversation_id`, etc.), not just
the documented `feedback` column.

**Why this is not an active hole today:** RLS is the actual gate, and it is sound. `user_profiles`
has **no INSERT policy at all** for `authenticated` or `anon` — with RLS enabled and zero
matching policies for a command, Postgres denies that command outright regardless of column
grants. Same logic protects `messages`: `anon` has no policy of any kind on it, so the broad
column grants are inert.

**Why it is still a real finding:** the original audit's "column-level GRANTs (defense-in-depth)"
framing implies these grants are the second line of defense if RLS is ever misconfigured. In
practice, the column grants are far broader than that framing suggests — they are effectively
"default Supabase/PostgREST grants, never tightened," with RLS carrying 100% of the actual
protection rather than sharing the load. If an INSERT policy is ever added to `user_profiles`
without care (e.g. to support some future self-serve profile-creation flow), the pre-existing
broad column grant on `role` would immediately make that policy exploitable for
privilege escalation, because the grant work to prevent it was never done. This is a **gap
needing human review**, not an active vulnerability: tighten `REVOKE INSERT, UPDATE, SELECT,
REFERENCES` down to the actually-needed column set for both `anon` and `authenticated` on both
tables, as a hardening pass — good scope for DEU-95 or a new item, human call.

## 7. Credit/usage-cap code path — DEU-38/DEU-52 resolution

**One-paragraph answer:** the Market Intelligence per-user run cap (DEU-52) operates **entirely
independently** of the coaching-chat credit system. `chat/index.ts:93-119` gates on
`fn_reset_credits_if_due()` (a `SECURITY DEFINER` RPC reading/writing `user_profiles
.credits_remaining`) and **fails open** on error (`chat/index.ts:108-111`: "Best-effort: fall
through to unlimited rather than block the user on a transient DB issue"). `market-intel
/index.ts:419-456` instead counts lifetime `model_usage` rows where `call_type =
'market_intel_research'` against a tunable `app_settings.market_intel_run_cap`, and **fails
closed** on the same class of error (a deliberate reversal, stated explicitly in the migration
comment for `20260710090000_market_intel_run_cap.sql`). The two mechanisms share no code, no
table column, and no failure posture. `competitive-intel/index.ts:462-487` and
`competitor-profile/index.ts:334-359` mirror `market-intel`'s pattern exactly, each with its own
`app_settings` key (`competitive_intel_run_cap`, `competitor_profile_run_cap`,
`competitive_gap_run_cap` — the third confirmed via
`20260710100000_competitive_intel_run_caps.sql`), each counting its own `call_type` in
`model_usage`. A repo-wide grep for the three markers (`run_cap`, `credits_remaining`,
`fn_reset_credits_if_due`) across every Edge Function returns exactly six files: `chat`,
`market-intel`, `competitive-intel`, `competitor-profile`, `competitive-gap`, and
`admin-users` (which only performs credit resets, not gating). **`discovery-turn` and
`assumption-mapping` have zero gating of any kind** — confirmed by absence from that same grep,
matching DEU-52's own description of the accepted gap ("low-cost per call and not the
concern"). This resolves DEU-38's open verification item: the recurring demo cap is *not*
"partially built" in the sense of one shared mechanism half-covering the surface — it is five
**separate, fully-built, working caps** covering the five expensive call types, deliberately
not extended to the two cheap ones.

## 8. Storage — objects, orphans, correction to an earlier claim in this conversation

Live query (join `storage.objects` to `public.documents` on `file_path`):

|---|---|---|
| `.../The_Entrepreneurs_Guide_to_Customer_Development.pdf` | `9cc622cb-e9a9-423d-80d8-4bfac74b890e` | **Yes** — `2a3792da-b520-4d9f-b04a-153822b90456` |

**Zero orphans.** The single object in the bucket has a matching `documents` row.

**Correction:** earlier in this session, before this diagnostic ran, I told Mo the bucket held
"1 object but the `documents` table has 0 rows — an orphan." That claim was wrong. It was built
from two separate observations (a live `COUNT(*)` on `storage.objects`, and a `list_tables` row
estimate for `documents` showing `0`) without ever actually joining them. The `list_tables` row
count is a Postgres planner estimate (`reltuples`), not a live count, and is unreliable for
small, rarely-`ANALYZE`d tables — this session's `list_tables` call showed `documents: rows: 0`
and `storage.objects: rows: 0` simultaneously, while a direct `COUNT(*)` on both returns `1` for
each. **Do not trust `list_tables` row counts for small tables; use `COUNT(*)` directly when a
number matters.**

Bucket config: private, 50MB limit, `application/pdf` + `text/plain` only — matches CLAUDE.md.
