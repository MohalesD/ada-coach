The 53-Second Hang

One request to Anthropic that never came back, and the two lines of policy that were missing.

11 September 2026 Component _shared/anthropic.ts Found by the first live bridge run Author Mohales Deis

What happenedA first read that never arrived

A product manager sent an idea from Builder Journal to Ada. The bridge did its job: it created the account link, the product, the sprint and the conversation, then called Anthropic to generate Ada's opening read so it would be waiting when they got there.

That call never came back.

04:19:03  stage_classification recorded, sprint created
04:19:56  kickoff coach turn failed: Error: Anthropic API 500
          at callClaude (_shared/anthropic.ts:24:11)
          at async kickoffSprint (_shared/sprint-kickoff.ts:74:13)
04:19:56  bridge-intake kickoff skipped: model_failed
04:19:57  POST | 201 | /functions/v1/bridge-intake

Fifty-three seconds inside a single fetch, and then a 500 carrying {"type":"timeout_error","message":"Request timeout"}.

Ada's design held, and that is worth saying plainly because everything after this is a criticism. kickoffSprint never throws; it returns { error: true, reason } so the sprint survives a failed read. The bridge returned 201, the PM landed in a real sprint with their idea and the starter questions, and nothing was corrupted or lost.

Then it happened again, on their first message in that sprint. They saw "Ada is taking a moment. Your message is in the thread, try again." They refreshed, which did nothing, because the message had already been saved and the failure was on the reply. They pasted it again.

The evidenceThree attempts, drawn to scale

One user, one idea, four minutes bars to scale · 0 to 63s
Attempt 1automatic, on arrival 53s · 500 timeout_error
Attempt 2starter question 63s · 500 timeout_error
Attempt 3same text, pasted again 6s

Nothing about the request changed between attempt 2 and attempt 3. Same model, same prompt, same account. The fault was transient, upstream, and it cleared on its own.

A transient fault that clears on retry is the most forgiving kind of failure a system can have. Ada turned it into a two-minute ordeal for a first-time user, because the user was the retry mechanism.

Root causeTwo things that were not in the code

  • No timeout. fetch was called with no signal, so nothing bounded a single attempt. Anthropic's own server-side timeout is what eventually ended it, at 53 seconds.
  • No retry. One failure was the final answer. The user retried by hand, twice.

The second is the one that matters for a coaching product. Ada's whole premise is that she has already read your idea by the time you arrive. When the read fails she has not lost a feature, she has broken the promise the arrival was built on. Making that promise depend on a single un-retried network call was the actual defect.

The fixA bound, and one second chance

signal: AbortSignal.timeout(timeoutMs)   // default 20_000

Why 20 seconds. A normal Haiku coaching turn on a sprint intake measures 5 to 7 seconds in this codebase, so 20 sits comfortably above the real p99 and will not cut off a slow-but-healthy call. It is also far enough under the edge gateway's own idle limit that a failed attempt leaves budget to try again, which a 50-second timeout would not. The number is a compromise between two ceilings, not a round guess.

Which faults get a second chance

StatusRetryWhy
nullyesNo response at all: our own abort, or a dead socket. This is the 53-second hang.
408yesRequest timeout, theirs this time.
429yesRate limited. A moment is exactly what it needs.
5xxyesThe server having a bad moment, including the 500 timeout_error that started this.
400 / 401 / 403 / 404noA statement about the request itself: malformed body, bad key, blocked model. Fails identically the second time; retrying only doubles the wait before the caller finds out.

What one retry actually costs

Do the arithmetic rather than trusting the intuition. Two attempts that both time out cost 20 + 0.6 + 20 = 40.6s and still end in a failure. That beats 53 seconds, but only a little, and latency is not where the win is.

The win is that the realistic case stops being a failure at all. One upstream blip followed by a healthy call now ends in a first read at about 26 seconds instead of no first read. Trading a 53-second failure for a 26-second success is the entire return on this change.

A third attempt would push the worst case past a minute, which is worse than where we started, and if two attempts 600ms apart have both failed the fault is usually not the kind a third will clear.

What deliberately did not change

  • The error shape. A final failure still throws Anthropic API 500: …, so every existing catch site behaves exactly as before, including the non-fatal kickoff path that reads it. The fix changes how often failure happens and how long it takes to arrive, not what it looks like.
  • callClaudeWithWebSearch is untouched. Grounded research calls legitimately run 60 to 120 seconds and carry their own continuation budget. A 20-second bound there would break working behaviour.

One more caseAn empty reply is a failure too

A 200 whose content array is empty is an HTTP success with nothing in it, usually a truncation or a content filter. The old code already threw on it; it is now marked retryable, because it is the same class of problem as a dropped socket. The request was fine, the response was not, and asking again often works.

VerificationWhat was proven, and what was not

Twelve tests in _shared/anthropic.test.ts, ten confirmed to fail against the previous version: the abort signal reaches fetch, the budget sits between 10 and 60 seconds, a 500 timeout_error followed by a success recovers in two calls, an aborted attempt is retried, a 400 is not retried and fails in one call, an empty reply is retried, the final error still matches /^Anthropic API 500:/, and maxAttempts: 1 turns the retry off. Type-check clean, full suite passing, build clean.

Not verified: the fix against a real upstream outage. That fault lasted about two minutes and cannot be summoned on demand. The tests prove the policy; only the next outage proves the outcome.

ScopeWhat this does not fix

Retries reduce how often the first read fails. They cannot make it never fail. Two things stay true, and both are handled on the Builder Journal side rather than here:

  • The tab that waits for the handoff now escalates its copy at 14 and 40 seconds instead of promising "about ten seconds" indefinitely.
  • Builder Journal now surfaces kickoff: { error: true } instead of discarding it, so a PM who arrives without a first read is told so rather than left to wonder.

Those are documented in The Last Mile of a Cross-Product Bridge. That document and this one are two halves of the same incident: one app made the failure less likely, the other made it legible.
